The problem

There is no fixed-point DPI type

DPI-C defines an exact C mapping for a fixed set of SystemVerilog types. ap_fixed is not among them — it is a C++ class template, not a language type.

ap_fixed lives only in C++

  • A class template: ap_fixed<W,I,Q,O,N>
  • W, I, Q, O are compile-time parameters.
  • No matching SV type, no DPI mapping, no vendor wrapper.
Consequence: the boundary cannot carry fixed-point objects. It carries the only thing both sides agree on: bits.
Project finding: Xcelium 26.03 and IXCOM 26.07 provide no fixed-point DPI mapping.
Two worlds

The same value, described twice

Each side knows something the other does not. The DPI boundary is where the two descriptions meet.

SystemVerilog side — bits, no binary point

  • int a_data[1024]; — 32-bit, 2-state
  • wire [10:0] a_dout; — 11 raw bits
  • wire [20:0] c_din; — 21 raw bits
It can slice, widen and compare. It cannot say “this word means 0.7”.

C / HLS side — format is part of the type

  • ap_fixed<11,1,AP_RND,AP_SAT> — 11 bits, 10 fractional
  • ap_fixed<21,1,AP_RND,AP_SAT> — 21 bits, 20 fractional
  • Assignment applies rounding and saturation.
It can multiply, round and print. It cannot see 4-state logic or X.
Contract at the boundary: the DPI word holds the W-bit two’s-complement raw value. The binary point is metadata and never crosses. Decoding it is the C side’s job.
Decoding the type

ap_fixed in one slide

Three numbers describe the whole format: the word width, the integer width, and the gap between them.

W total bits
I integer bits (sign included)
F = W − I fractional bits
value = raw / 2F
raw = value × 2F
Type in hls/define.hDeclaration WIFLSBRange
data_t ap_fixed<W+1,1,AP_RND,AP_SAT> 11110 2⁻¹⁰ ≈ 9.766e-4 [−1, 0.9990234375]
out_t ap_fixed<2*W+1,1,AP_RND,AP_SAT> 21120 2⁻²⁰ ≈ 9.537e-7 [−1, 0.9999990463]
W = 10 in define.h, so data_t is W+1 = 11 bits wide.
I = 1 means the only integer bit is the sign bit. Both types hold fractions in [−1, 1).
Q / O apply on assignment: AP_RND rounds to nearest, AP_SAT clamps on overflow.
What HLS generates

HLS flattens ap_fixed to plain wires

The DUT is compiled with FIFO interfaces. Every ap_fixed port becomes a W-bit wire; the format disappears.

#pragma HLS INTERFACE ap_fifo port=a,b,c
#pragma HLS INTERFACE ap_ctrl_none port=return
#pragma HLS PIPELINE

for (int i=0; i<N; i++)
#pragma HLS UNROLL off
    c[i] = a[i] * b[i];

The synthesised DUT carries no format information. All binary-point bookkeeping happened inside HLS at compile time; the testbench only wires bits.

Port width

W bits, exactly the raw word — no padding, no scale factor.

Product

11s × 11s gives a 22-bit product (dut_mul_11s_11s_22_1_1).

Output

Rounded and saturated to 21 bits by select_ln11.

The bridge rule

One element = one raw word

Everything in this deck follows from four rules. They fit on a napkin.

01 · CARRIER

If W ≤ 32, use one int per element — a 32-bit two’s-complement word.

02 · PLACE

Keep the raw word in the low W bits. High bits are padding.

03 · READ

Mask when reading. Never trust whatever sits above bit W−1.

04 · SIGN

Signedness is interpretation, not transport. The bits are neutral.

int word for a, b — 32 bits raw 0x2CD
int word for c — 32 bits raw 0x35BD7
raw ap_fixed<11,1>, bits 10…0 raw ap_fixed<21,1>, bits 20…0 unused / sign extension — mask before use
The bits alone are ambiguous. 0x2CD means 717 only because F = 10. Under F = 20 the same word would mean 717 / 2²⁰ ≈ 0.000684.
The conversion map

Who converts what

Only the two quantizers change a numeric value. Everything else is a copy, a slice, or a mask.

Why it works

The round trip is the identity

For any W-bit word, ap_fixed → int → ap_fixed reproduces the same bits. No arithmetic is involved.

src/cpp/dpi_hls_model.cppraw-bit helpers
int      w = raw_bits(va);   // low 11 bits, e.g. 0x2CD
data_t   x = from_bits(w);   // same 11 bits inside ap_private<11,true>
// always true for W <= 32
assert(raw_bits(x) == w);

Bits in

The low W bits of a 32-bit int. The rest is ignored.

Bits stored

ap_private<W,true>: pure two’s-complement storage inside the object.

Bits out

get_VAL() & (2W−1). Same W bits, no scaling.

Because the path is lossless, a mismatch in the scoreboard is a real model or RTL bug — not a conversion artifact.
Converting C → ap_fixed

from_bits(): stuff the raw word

Put the bits into the object’s storage and let the type interpret them.

src/cpp/dpi_hls_model.cpp:50C++
static inline data_t from_bits(int v)
{
    data_t x;                                    // ap_fixed<11,1>
    x.V = ap_private<W + 1, true>(
              (unsigned long long)(uint32_t)v);  // low 32 bits only
    return x;
}

Why each piece is there

  • x.V is the raw container: ap_private<11,true>.
  • (uint32_t) stops sign extension — −1 contributes exactly 0x7FF.
  • Vitis HLS 2025.2 C simulation has no public set_raw(); writing V is the working route.
Writing V bypasses AP_RND/AP_SAT. The bits are taken verbatim — exactly what a scoreboard needs.
For W > 32 pass a uint64_t word instead of casting through uint32_t. Above 64 bits, use the packed-vector route on slide 16.
Converting ap_fixed → C

raw_bits(): mask, then move

get_VAL() returns a sign-extended 64-bit view. The mask recovers the W-bit word.

src/cpp/dpi_hls_model.cpp:37C++
static inline unsigned raw_bits(const data_t& x)
{
    return (unsigned)((unsigned long long)x.V.get_VAL()
                      & ((1ULL << (W + 1)) - 1));
}

Sign extension leaks

Raw 0x7FF (= −1) comes back as 0xFFFF_FFFF_FFFF_FFFF. Mask it.

Mask = 2W − 1

Here (1ULL << 11) − 1 = 0x7FF: exactly the type width.

No floating point

No division by 2F, no double. A pure bit copy.

The result is returned unsigned on purpose: transport is unsigned, interpretation comes later. Call sign_extend() only when the sign matters.
Comparing results

Sign-extend both sides to the same width

The scoreboard compares 21-bit words, so both values are normalized before the ==.

src/cpp/dpi_hls_model.cpp:43, 88C++
static inline int sign_extend(unsigned v, int bits)
{
    const long long m   = 1LL << (bits - 1);          // 0x0010_0000
    const long long val = (long long)(v & ((1u << bits) - 1));
    return (int)((val & m) ? val - (1LL << bits) : val);
}

// both sides normalized to 21 bits before the compare
const int exp = sign_extend((unsigned)cc[i].V.get_VAL(), 2*W + 1);
const int got = sign_extend((unsigned)(uint32_t)c_hw[i], 2*W + 1);
if (exp != got) ++errs;
Mask first, interpret second. Both operands go through the same 21-bit mask; the comparison then means “same two’s-complement word”.
Do not skip the mask. A sign-extended SV value and a zero-extended C value differ for every negative result — the test would fail for the wrong reason.
The SystemVerilog side

Slice in, sign-extend out

The testbench does no arithmetic either — just a part-select and a cast.

src/v/Tb_hls.sv:49, 70SystemVerilog
// int -> 11-bit wire: take the low bits (no arithmetic)
wire [10:0] a_dout = (rd_idx < N) ? a_data[rd_idx][10:0] : 11'd0;

// 21-bit wire -> int: make the vector signed, then widen
always @(posedge clk)
  if (c_write && wr_idx < N)
    c_hw[wr_idx] <= $signed(c_din);

Part-select = truncation

[10:0] throws away high bits. Safe here: the int already holds only 11 significant bits.

$signed changes meaning

It does not touch the bits; it makes the following widening sign-extend instead of zero-extend.

Free-running port

ap_ctrl_none: c_din is combinational and valid in the c_write cycle.

With a 21-bit unsigned vector, any negative product would arrive as a large positive int (2²¹ − |c|). $signed() is what makes the scoreboard’s signed compare meaningful.
Worked example · exact

Powers of two: no rounding at all

A value is just its raw word scaled by 2−F. Choose exact inputs and the whole chain is trivial.

SignalValueFRaw (dec)Raw (hex)Raw (binary, W bits)
a0.510 5120x0200 010_0000_0000
b0.2510 2560x0100 001_0000_0000
c0.12520 1310720x2_0000 0_0010_0000_0000_0000_0000
craw = araw · braw · 2Fout − 2·Fin

Here Fout = 2·Fin, so the scale factor is 2⁰: the output raw word is simply the integer product of the input raw words.
On the wire: a_dout = 11'h200, b_dout = 11'h100, c_din = 21'h20000. The SV testbench never knows these are 0.5, 0.25, 0.125.
Worked example · quantization

Round once, then stay exact

Real-valued stimulus has to be quantized when it enters ap_fixed. After that, every step in this chain is integer-exact.

SignalReal value× 2FStored in ap_fixedRaw word
a0.7716.8 AP_RND → 7170x2CD
b0.3307.2 AP_RND → 3070x133
c0.209982872…220119 exact at F = 200x3_5BD7
Why the output is exact: 717 × 307 = 220119, and 220119 < 2²¹. The 22-bit product needs no rounding at 21 bits.
The RTL applies the same quantization to the 22-bit product (dut.v: tmp/select_ln11) — same bits, same result.
AP_SAT in practice: the stimulus (rand()%N + 1.0)/N can produce exactly 1.0. ap_fixed<11,1> cannot represent 1, so it clamps to 1023/1024 = 0x3FF. With 1024 random values this is very likely to occur.
Alternative path

You can use double — know what you give up

SV real maps to C double, and ap_fixed converts to and from it implicitly. It is convenient, but it is not a wire.

value-domain routeC++
// SV: import "DPI-C" function void take_real(input real r);  // C: double r
data_t va = (std::rand() % N + 1.0) / N;  // double -> ap_fixed (AP_RND / AP_SAT)
double d  = (double)va;                    // ap_fixed -> double

When it is fine

  • W ≤ 53: a double’s 53-bit significand holds every raw value exactly.
  • Here W = 11 and 21, so the route is numerically exact.
  • Useful for logging, plotting and readable stimulus.

What you lose

  • Above 53 bits the conversion is silently lossy.
  • You compare numbers, not the exact words the RTL produced.
  • shortreal ↔ float is only 24 bits — worse.
  • Every element goes through floating-point conversion.
From this project’s notes: “For W ≤ 53 the double path is numerically exact here, but raw bits are the general / bit-accurate option.” Rule of thumb: raw words on the boundary; double only for printing.

The DPI contract

Signature rules that bite

The SV declaration and the generated header are the real contract. Get them wrong and the library loads, then misbehaves.

Open arrays become pointers

The [N] disappears: size is not part of the ABI. C receives int*.

Function vs task (IXCOM)

A DPI function may take only input arguments. For data flowing C → SV, use a task with output/inout, or an export callback.

context routines

Required to call back into SV (exports, PLI). Both routines here are context; non-context calls are cheaper where no callback is needed.

-dpi_void_task

Without it, an imported task returns int. The Makefile passes it, so the header says void.

dpi_import.hgenerated by xmelab
/* do not edit — generated */

                                 int *_a3);
extern void tb_gen_stim (int *_a1, int *_a2);
Match the header exactly. Compile the C model against the generated file, not a hand-written prototype — this is your only compile-time check.
Scope matters for exports: declare the import inside the module whose scope exported routines are resolved in (see Tb.sv), or export at $unit.

Checklist

Eight ways to get this wrong

All of these compile. Most of them fail only at simulation time, or worse, pass with wrong data.

1 · Fixed-point in a signature

No DPI mapping exists. Pass bits.

2 · Unmasked get_VAL()

Sign extension pollutes the high bits.

3 · No uint32_t cast

Negative ints leak ones past bit W−1.

4 · Missing $signed()

Negative products appear as huge positives.

5 · Comparing raw widths

Mask both sides to the same W first.

6 · Confusing I with F

F = W − I. I includes the sign bit.

7 · Expecting Q/O on .V

Writing the raw container bypasses rounding and saturation.

8 · Wrong vector type

svBitVecVal for 2-state; svLogicVecVal needs bval.

Debug heuristic: if only negative values fail, think sign extension. If only wide values fail, think masks. If nothing fails but the numbers are off by 2F, think binary point.

The type table is small enough to memorize, and the conversion is smaller still.
